# P3-M10 architecture

Status: Done

The application owns which open locations need watching and whether an invalidation should start a read. A desktop watcher observes native changes or runs bounded fallback checks, then reports facts through the existing serialized event boundary. The [overview checklist](milestone-10-overview.md#completion-checklist) is the executable definition of done.

## Application contract and watch lifecycle

Add typed `WatchLocation { location, generation }` and `UnwatchLocation { location, generation }` work requests, and generation-tagged watcher-ready, status, and invalidation events. Keep the existing `Event::LocationInvalidated` for operation-lane facts; the new watcher event validates its generation before using the same refresh path. The generation belongs to the application subscription, not a native handle. The application maintains a set of desired byte-exact `Location`s from each tab's displayed location and pending target. It diffs this set after each transition: new watches precede directory reads in dispatch order, and removed watches stop after the transition. Two tabs at the same location share one subscription; removing one tab does not stop the other's watch. A pending navigation retains the watch for its last successful rows until the new folder succeeds, while also watching the target. A failed first read retains its requested location so it can be retried.

The desktop keeps native handles, subscription generations, polling deadlines, and mount observations outside application state. A callback with an old generation, or for a location no longer desired, changes nothing. Stop and shutdown close handles asynchronously without joining a native callback on the GUI thread. A watch-ready event invalidates its location once, closing the race where a read finished before monitoring became active. Root changes, dropped notifications, wrapped event IDs, reconnects, and remounts similarly cause a full read of each affected open location rather than trying to apply event paths as row edits. A root change, dropped/coalesced history, or wrapped event ID also tears down the affected native stream and uses the periodic path until a fresh stream can be registered.

Add a dirty bit to each pending tab read. `LocationInvalidated` starts a read for an idle matching tab and marks a matching in-flight read dirty without cancelling it. On its terminal result, the reducer applies the result under the existing token rules, then issues one follow-up read if dirty and still at that location. Coalesced invalidations during that follow-up can request another completed read, but no event restarts the current one. A superseding navigation, sort, or manual refresh clears the old dirty bit; a stale result cannot start work. A failed read keeps the existing rows and error. Retry after repeated failures follows bounded watcher backoff, so a continuously unavailable folder does not create a tight loop. Operation-triggered refreshes keep their current affected-location semantics and may satisfy a pending invalidation for that same location.

The application's watch status is `Native`, `Periodic`, or `Unavailable` per location. The active tab projects the status into the Browser Status Bar; loading and directory-read errors take precedence over it. The adapter supplies the wording: “Checking for changes periodically” for a working fallback and “Automatic refresh unavailable — Command+R to Refresh” when both native and fallback checks are unavailable. Status changes for inactive tabs become visible when activated; no Notice or persisted setting is added.

## Desktop watcher and scheduling

Use a dedicated CoreServices FSEvents service, dynamically linked through the existing desktop build. The native callback only maps a stream to its subscribed logical location and enqueues a keyed invalidation. It does not enumerate, sort, mutate workspace state, or invoke Qt directly. FSEvents provides directory-hierarchy notifications; the listing worker remains the authority for actual rows. Request root-change notifications, treat dropped or coalesced events as full invalidations, and keep native callback work bounded. [Apple's FSEvents guide](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html) describes the stream lifecycle, rescan requirement, root-change flag, and dropped-event recovery.

Convert paths without using lossy display text. If a location cannot be represented by the native stream, if its volume does not supply usable notifications, or if registration fails, use periodic checking on a bounded worker lane. Recheck mount identity and watcher availability after disconnect, remount, wake, or a stale-mount error; never interpret an old callback as proof that a newly mounted volume is unchanged. For a missing location, keep the requested path and retry registration or checking when its parent changes and on the next scheduled check. Native watching and polling are advisory; each signal requests a full worker listing, preserving the application's failure and selection rules.

While the app is active, schedule fallback checks with jitter: a visible tab begins at about 5 seconds, and an inactive tab at about 60 seconds. Repeated failures back off exponentially to at most 5 minutes; a successful check returns to its base interval. Polling uses bounded read admission and never creates a thread per tab or mount. When the app becomes hidden or loses focus, retain native subscriptions but suppress fallback checks and watch-triggered reads, holding at most one dirty indication per location. On return, invalidate every desired location once and resume the appropriate deadlines. Native callbacks are coalesced by location in a finite map before GUI delivery; terminal read results remain deliverable and take priority. Saturation leaves a location dirty for a later bounded retry instead of spinning or dropping the need to reconcile.

## Implementation sequence and verification

1. Add the application watch-set diff, generations, status projection, and dirty-read behavior with Qt-free tests. Preserve the existing `WorkRequest::ReadDirectory` and token semantics.
2. Add a fakeable watcher scheduler and native FSEvents adapter, connect it to `Runtime` and `WorkspaceSession`, and wire application activity from the desktop shell. Keep native handles and mount probes off the GUI thread; no new crate or build tool is required.
3. Add presenter status wording and focused lifecycle tests, then temporary-directory native tests. Perform the human check and full repository gate named in the overview before checking completion items.

The main risks are a setup gap, callbacks after unwatch, a hot folder that continually invalidates, and an unavailable remote mount. Generation checks, a watch-ready reconciliation, finish-then-reread scheduling, bounded polling, and retained last-successful listings address those cases.
