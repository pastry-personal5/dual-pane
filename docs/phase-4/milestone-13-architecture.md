# P4-M13 architecture

Status: Active

The application owns the per-content-type menu policy and captures one-use Open With intentions; a macOS adapter resolves types, candidates, and defaults and performs opening and confirmed default changes. The Settings page and native menus render projections rather than making policy decisions. The [overview](milestone-13-overview.md) is the acceptance contract.

## Identity and platform boundary

- Use the file's macOS `UTType.identifier` as the policy key. Resolve a real file from its URL resource `contentType`, including for a link to a regular-file target. If that resource value is unavailable for an otherwise verified regular file, ask macOS's UTI registry for its filename extension as a compatibility fallback; never use a Dual Pane extension mapping. Capture both a selected link's identity and its resolved target identity, and pass the target URL to the opener as the existing Open Item behavior does. Reject missing, inaccessible, undecodable, directory, and package targets with typed outcomes. Do not resolve link targets for Copy, Move, or other existing operations.
- Query `NSWorkspace.urlsForApplications(toOpen: UTType)` for the ranked type candidates and `urlForApplication(toOpen: UTType)` separately for the type default. For a multi-file selection, require one exact type identifier and intersect the file-based candidate sets so every offered application can open every file. If macOS returns no URL-specific candidates for an otherwise resolved file, use its macOS type-candidate list for that file's set; preserve the type-based rank for common apps. The candidate array's first member is not treated as proof of the current default.
- Model an application by bundle identifier plus its registered bundle URL so two installed copies cannot silently substitute for one another. Keep the exact registered URL in the menu observation. A moved application may be remapped by bundle identifier only when one unambiguous current candidate exists; otherwise show the saved choice as unavailable until the user selects an available candidate. Display labels come from the system; disambiguate equal labels with location text.
- Add an Objective-C++ adapter beside the existing AppKit integrations. It bridges exact file-system paths and typed results to Rust without parsing Launch Services stores, invoking `lsregister`, or adding a dependency. Keep platform objects out of the Qt-free application and adapter crates.

## Work scheduling and snapshots

- Observe types from successful, already available listings across open tabs. A bounded dedicated background queue deduplicates file paths and type identifiers and does not recursively walk directories. A chosen sample file uses the same resolver and pins only its type identifier. File information and Launch Services reads do not run in the synchronous menu request or Settings paint path.
- Cache type descriptions, ranked candidates, the type default, and file-specific candidate identities with listing generations and explicit loading/error state. Refresh on a completed listing, Settings-page entry, a user request, and a completed default change. A late listing result is ignored when its originating observation is gone. No candidate query occupies the file-operation lane.
- Expose typed application requests/results for discovery, open with chosen app, and default changes. Settings uses the same loaded catalogue as menus, with a revision so controls update in place without losing focus or scroll. A menu request reads only the latest completed cache; pending discovery emits no app action token. The setup action opens File Associations Settings with an identifying-type state if needed. Do not live-update an open `QMenu`.

## Application policy and persistence

- Add `FileAssociationPreferences` keyed by content-type identifier. Each type has a pin and independent sets of selected application identities for Normal and Comprehensive; both sets start empty. An app installed later is unchecked until the user selects it. Clearing one or both sets is valid and does not switch to an implicit display-all mode.
- An observed type edited in Settings becomes pinned so it remains listed after its source tab closes, even when the final app is unchecked. Folder listing refreshes retain the previous observed-type snapshot until the new lookup succeeds, then replace that folder's snapshot as one update; an empty listing retires it immediately. Background observation keeps one active lookup per byte-exact folder, ignores an unchanged file set, and retains only the latest changed set behind an active lookup. A rejected observation retries after 1, 2, 4, 8, 16, 32, then 60 seconds, capped at 60 seconds until success; a changed listing updates the retry payload, and closing or emptying the folder invalidates its timer. Explicit Refresh Applications remains immediate. Add File Type also pins a type; Clear Open With Choices empties both selected sets but keeps the pin, and Remove Type deletes its pin and local choices after confirmation. Global Reset Settings restores empty local associations. No settings snapshot contains the macOS default as a writable value; failure or cancellation of a default change does not save a claimed default.
- Migrate SQLite schema 11 to 12 with a type table containing the identifier and pin, and a child table for selected app identities keyed by type and menu kind. Empty child sets are valid. Validate bounds, identifiers, menu kinds, duplicates, foreign keys, and parent/child consistency before publishing a loaded snapshot. Save in the existing transaction; an invalid or failed save changes no durable preference. Fresh and all supported older profiles receive empty associations, which means no app rows until selected.
- Add `ConfigureOpenWith` as one static `ActionId` in the M11 action catalogue, with no default shortcut, in the Open group and enabled by default in both menu variants. It uses the ordinary Context Menus Settings visibility controls. Schema 12 adds its two default-visible `context_menu_action` rows during migration without changing existing choices. Add a distinct dynamic menu-entry payload for `OpenWithApp`, with an application-owned display/dispatch token; individual apps are not `ActionId`s and are controlled by File Associations Settings. The existing requirement that each menu retain one configured static action stays intact.

## Menu and effect flow

- On a menu request, apply the existing secondary-selection rule. The catalogued setup action is available for an eligible captured regular-file selection, subject to that variant's Context Menus visibility choice, and opens File Associations Settings focused on its type. It is independent of the app checkbox sets. App rows require one exact resolved type and a common available-app set across selected files. Filter the rank-ordered candidates by that type's selected app identities for the requested variant. Insert flat `Open with <app>` entries after Open Item, followed by the setup action, in the Open group. Collapse empty groups and separators as before.
- Store the emitted app identities in the same one-use menu observation as the static commands, along with exact Browser, tab, listing revision, selection names and kinds, source folder, resolved type when ready, and source file identities. A chosen app token must have appeared in that snapshot. The Configure Open With action uses the captured selection, not the selection at Settings-opening time: after dispatch-time observation checks, it opens File Associations Settings in an identifying-type state if needed, resolves the captured files asynchronously, then focuses that type; a changed or mixed selection reports a reason instead of choosing a different type. Recheck that the tab, selection, files, link targets, and types still match and the app remains a registered eligible candidate before handing exact file URLs to the native effect. Repeat, retired, changed, or foreign tokens do nothing and produce appropriate feedback.
- Use `NSWorkspace.open(_:withApplicationAt:configuration:completionHandler:)` for a one-time open. Dispatch asynchronously and marshal its completion back to the application; report errors in Notices. A success means macOS accepted the open request, not that the external app displayed or parsed every document.
- Set as Default is separate from menu invocation. The Settings confirmation freezes type and app identity; acceptance starts `NSWorkspace.setDefaultApplication(at:toOpen:completion:)`. Present busy state, handle its consent/error completion, then read `urlForApplication(toOpen:)` again. Publish success only for the requested default; a mismatch or error remains visible and can be retried. On success invalidate the relevant candidate/default cache. Never synthesize a per-file override or try to restore an earlier macOS default during a Dual Pane settings reset.

## Verification and delivery order

1. Add Qt-free association policy, the catalogued Configure Open With action, typed work/effect contracts, and application tests. Define the static/dynamic menu-entry boundary before native UI changes.
2. Add schema-12 migration and storage tests, then the bounded AppKit discovery/open/default facade with fakeable results for ordinary tests. Existing Objective-C++ build support is sufficient; any genuinely new dependency or build tool needs owner approval under `AGENTS.md`.
3. Add the Settings page and flat menu rows, preserving the existing non-blocking `QMenu::popup` lifecycle and stale-observation validation. Extend the disposable native Settings and Context Menu checks.
4. Run the full gate once after implementation, then record guided macOS acceptance separately. Automated tests use temporary files and never call the real default-change API against the user's Launch Services database.

Apple documents the [ranked candidate list](https://developer.apple.com/documentation/appkit/nsworkspace/urlsforapplications%28toopen%3A%29-60rkm), [one-time open](https://developer.apple.com/documentation/appkit/nsworkspace/open%28_%3Awithapplicationat%3Aconfiguration%3Acompletionhandler%3A%29), and [type-wide default change with possible system consent](https://developer.apple.com/documentation/appkit/nsworkspace/setdefaultapplication%28at%3Atoopen%3Acompletion%3A%29). The existing [research note](../research/file-type-default-app-research.md) provides background and warns against direct Launch Services database edits.
