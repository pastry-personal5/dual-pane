# P4-M10 architecture

Status: Active

The application owns two persistent Folder Items menu configurations and produces one immutable, observation-tagged menu snapshot for the desktop to render. Qt classifies the native invocation, asks for that snapshot, and draws it; it does not decide command availability, grouping, targets, or settings validity. The application, schema-11 storage, snapshot/token path, Settings projection, and owned asynchronous native renderer are present. The [overview checklist](milestone-10-overview.md#completion-checklist) defines the remaining acceptance work.

## Current implementation baseline

The implementation provides the eleven-action catalogue and defaults, preference validation and mutation commands, schema-11 creation/load/save, typed request/invoke/dismiss commands, grouped snapshots, one stored live token, action allow-listing, observation revalidation, the synchronous GUI-thread request bridge, and a shared `QContextMenuEvent` renderer for both Browsers. It also provides the adapter-owned Settings projection and rejection state, typed settings bridge, and third Settings page with its matrix and resets. Focused application, adapter, and storage tests cover settings mutations and resets, action contexts, selection timing, empty-space projection, shortcut metadata, one-use and stale observations, malformed rows, and every supported migration.

The renderer uses a workspace-wide owned `QMenu::popup` session with queued idempotent completion. Desktop shutdown explicitly dismisses the session while its model is alive. The separate acceptance script covers application policy plus real-widget lifecycle and routing without reading the global clipboard. Guided macOS acceptance remains.

## Settings model and persistence

The landed application types `ContextMenuKind`, `ContextMenuGroup`, and `ContextMenuPreferences` are keyed by the explicit `CONTEXT_MENU_ACTIONS` subset of the eleven existing `ActionId` values approved in the overview. That catalogue remains the one source of truth for eligible IDs, group/order, factory visibility, validation, and storage. Labels and native shortcut notation remain presentation concerns.

`SettingsState` owns the preferences with Favorites, shortcuts, and visibility policy. `SettingsSnapshot::default()` contains complete factory preferences, so fresh profiles and the many existing default-snapshot callers cannot create an invalid empty configuration. The typed commands change one action's visibility and reset Normal, Comprehensive, or both. A duplicate value is a no-op. A change that would leave one variant empty returns a typed rejection without increasing the settings revision or requesting a save. Global Reset Settings supplies `ContextMenuPreferences::default()` with the other compiled defaults.

The presentation path carries the ordered preferences in `WorkspaceChrome` and projects adapter-owned Context Menus Settings rows in `WorkspaceViewModel`, with dedicated preference and rejection revisions. One adapter label function supplies canonical action labels to both the menu bridge and Settings rows. The presenter consumes `ContextMenuPreferenceRejected` and exposes the rejected variant so the Settings page can restore the initiating checkbox and show the correct inline message. Accepted edits, loads, local resets, shortcut changes, and global Reset Settings update the relevant projection immediately; accepted preference changes use the existing save path, and no-ops or rejections issue no save. C++ does not reconstruct catalogue order, defaults, eligibility, labels, or validation policy.

The landed SQLite driver uses schema version 11. Its `context_menu_action` table stores menu kind, stable `ActionId` name, and visibility with a composite primary key plus kind and Boolean checks. The version-11 step creates the table and inserts both rows for every eligible action in the same transaction as the version change. Loading requires exactly one valid row per eligible action and variant and at least one visible action per variant. Extra or unknown kinds/actions, invalid Booleans, duplicates, missing rows, and empty variants are corrupt settings rather than silent policy changes. Saving validates first and replaces the rows in the existing settings transaction. Tests cover a fresh database and every supported schema through version 10, every malformed-row class, save rollback, relaunch, corrupt-database recovery, and newer-schema recovery. No dependency or build-tool change was needed.

## Menu projection and dispatch

The landed `RequestFolderItemsMenu` input contains the requested variant plus an observation of the source Browser, tab, visible revision, and invocation target. A row target carries the displayed row and exact `EntryName`; an empty-space target is explicit. Handling the request activates the source Browser, applies the existing secondary-selection rule for a valid row, and emits the menu result atomically. `BrowserSession` captures that output for the synchronous GUI-thread bridge request; the application reducer does not return a Qt model or expose a callback. A stale row observation emits no snapshot, so Qt cannot open a menu for a different Item after a refresh or tab switch. A keyboard or accessibility request is translated to the current cursor row when one is visible, otherwise to empty space. Tests cover both Browsers and the pointer, keyboard, accessibility, modifier, row, and empty-space routes.

The application produces a `FolderItemsMenuSnapshot` or equivalent from:

- the requested variant;
- the observed Browser, tab, listing revision, and row-or-empty invocation target;
- the exact current selection after the row-selection rule;
- application command availability, including the other Browser destination;
- cached clipboard offer state; and
- the effective ordered shortcut lists.

The application applies configured visibility and current availability, excludes selection actions from an empty-space invocation even though the selection is preserved, drops empty groups, and emits only nonempty groups. It returns no snapshot when no action remains. The request does no I/O and never synchronously refreshes the clipboard. Each row carries its stable `ActionId` and optional first effective `Shortcut`. The adapter supplies canonical labels and a portable key sequence; Qt converts that sequence to `QKeySequence::NativeText` for display without creating another binding.

Each nonempty snapshot receives a short-lived token and an allow-list of the actions actually emitted. Its observation retains only what dispatch needs: the exact tab and visible revision, the exact selection for source actions, the source location, and the other-Browser tab, revision, and location for transfer actions. The row and `EntryName` are request-time validation data; after the secondary-selection rule runs, listing revision plus exact selected names protect Item identity without retaining an unused clicked-row target. The CXX-Qt bridge exposes immutable groups/rows and sends only the token plus chosen `ActionId` back. Keep at most one stored Folder Items menu observation for the workspace. A newer request, matching dismissal, invocation, or shutdown explicitly retires it; intervening state may instead make it logically stale, which is safe only when dispatch revalidates every action-specific observation before doing work. An unknown, stale, retired, repeated, or non-emitted action is rejected. Do not scatter token-clearing calls across unrelated state transitions as a substitute for dispatch-time validation.

The landed inputs `InvokeFolderItemsMenu { token, action }` and `DismissFolderItemsMenu { token }` consume or retire the matching token. Command-specific validation checks current state: selection-dependent commands require the captured tab/listing and exact selection; Open Item and Show Package Contents require the exact captured single Item, with the latter still a package; Copy/Move to Other Browser also require the captured destination Browser, tab, revision, and location; and New Folder and Paste require the captured source tab and destination location to remain current, but do not become stale merely because irrelevant selection changed. They never fall through to a newly active tab. Paste then performs its ordinary fresh clipboard generation check and asynchronous read. A stale snapshot starts no editor, navigation, clipboard read, or file operation and changes no files. Existing command rejection and Browser Status Bar behavior remain authoritative after a valid snapshot reaches a command whose external conditions changed.

## Native interaction and Settings presentation

Route mouse, keyboard, and accessibility `QContextMenuEvent` entry through one `FolderItemsList` path, and suppress the old right-button `mousePressEvent` menu path so one gesture cannot open twice. Preserve the current selection timing: the application selection change occurs before the menu is displayed and remains if the menu is dismissed. Exact user modifiers after ignoring non-user flags such as `KeypadModifier` select Comprehensive only when Shift is the sole modifier; every other secondary invocation selects Normal. A non-pointer request anchors beside the visible cursor row, or at a documented inset within the viewport when there is no visible cursor. The same row-or-empty classification is sent to the application.

Render both variants through one owned `QMenu` session and the existing dark native style. Give them distinct accessible names without a visible heading. Render shortcut text in the native right-hand column without calling an API that registers another active shortcut. Open with non-blocking `QMenu::popup`; `QMenu::exec`, `QCoreApplication::processEvents`, and any other nested event loop are forbidden. The session records a chosen action from `triggered`, records closure from `aboutToHide`, and schedules one queued, idempotent finalizer from either signal. The finalizer acts only after closure is recorded; on that later GUI turn it submits exactly one token/action pair, or the matching dismissal if no action was chosen, then destroys the menu session. This makes correctness independent of signal delivery order and prevents `triggered` from dispatching while the menu is still open. A newer native request first closes and dismisses the prior session. Do not live-update an open menu; validity is checked when its action is submitted.

The third `SettingsWindow` page follows Keyboard Shortcuts Settings. Its scrollable categorized matrix uses the overview's Action, Normal, Comprehensive, and Shortcut columns. The bridge exposes rows from the adapter projection and typed mutation/reset methods; C++ does not identify eligible actions by duplicating string lists. Checkbox changes call the typed application command; a final-item rejection restores the checked state and shows “Normal Context Menu must keep at least one action.” or its Comprehensive equivalent inline until the next accepted edit, reset, category change, or window dismissal. Controls follow the existing `settings_interaction_available` state. The dedicated preferences and rejection revisions resynchronize existing checkboxes and shortcut labels in place after accepted edits, loads, resets, shortcut changes, and rejections, preserving keyboard focus and scroll position. Programmatic checkbox updates block signals.

Reset Normal…, Reset Comprehensive…, and Reset Both… each open a window-modal confirmation with Cancel as default and Escape button. Each confirmation names its exact scope; an accepted no-op reset makes no save request. Accepted resets leave the Settings Window open, clear rejection feedback, and immediately resynchronize the matrix. Use the existing Settings surfaces, cards, table headers, focus treatment, and compact controls; both menu preferences are global, not Browser-specific.
