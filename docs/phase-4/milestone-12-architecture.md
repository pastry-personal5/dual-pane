# P4-M12 architecture

Status: Active

Repair the native gesture boundary while retaining P4-M7's application-owned drag session and operation handoff. The [overview](milestone-12-overview.md) holds the accepted interaction decisions and completion checklist.

## Pre-implementation path and gap

Before M12, `FolderItemsList::mousePressEvent` in `cpp/include/dual_pane_desktop/folder_pane.hpp` set `drag_candidate_` only when the press had no user modifier. Its Command and Shift paths updated selection, then `mouseMoveEvent` could not start a drag from either press. `drop_modifiers_supported` and `drop_is_copy` in `gui_common.hpp` accepted only an exact no-modifier Move or exact Option-Copy. The native hover path ignored a drop move when `previewFileDrop` refused it. The Browser Tab path also checked the hover count before calling `acceptFileDrop` on release. Invalid native payloads and some bridge failures returned without a status reason. The application already emitted typed `DropRejected` output and the presenter mapped it to Status Bar text, but the event had to reach that path for the user to see it. The offscreen drag check called `beginFileDrag` and `acceptFileDrop` directly, bypassing the press/threshold path.

[Qt's drop-event contract](https://doc.qt.io/qt-6/qdropevent.html) requires the most recent drag-enter or drag-move event to be accepted before the widget receives a drop event. A refused preview therefore cannot simply call `ignore()` if the release must produce a reason. On macOS, [Control-click can produce a context-menu event](https://doc.qt.io/qt-6/macos-issues.html); synthetic `QMouseEvent`s cannot establish whether a physical Control-primary press reaches the left-button handler.

## Implementation approach

1. Keep the source-row, primary-button, and platform-distance guards in `FolderItemsList`, but allow a candidate with any modifier. Record the pressed row's stable identity, whether it was selected, the selected-root observation, Browser, tab, and visible revision before a nested native drag session can run. For a modified press, defer its ordinary selection gesture: release below threshold applies it once; crossing the threshold preserves the pre-press selection if the row was selected, or selects only the pressed row. Do not replay the click on drag completion or cancellation. Validate the observation when the threshold is crossed; if the row, view, or intended selection changed, decline to start rather than capturing a different selection. Keep native state path-free and let the application freeze roots. Verify whether a physical Control-primary press is remapped to a context-menu event on macOS; if so, handle its physical-button distinction at the native gesture boundary without changing actual secondary-click routing.
2. Keep `QDrag`'s private, path-free token and live source-widget provenance. `BeginDrag` still requires an identifiable source row and frozen source roots, but it must not reject a captured root solely because its kind cannot be transferred. Carry that fact in the application-owned session and return `UnsupportedSource` during preview and authoritative accept, so a release can explain the refusal. Do not weaken stale selection, duplicate-root, or source-identity checks. Continue to cancel the token when the platform drag session ends, including rejection or Escape; an accepted token is already consumed and cancellation is idempotent.
3. Replace the exact-modifier gate with one drop-action classifier in `gui_common.hpp`, used by Folder Items targets and `BrowserTabsStrip`. Derive preview text, accessibility state, `setDropAction`, and the accepted `DropAction` from the same classification at each event. Option present at the drop event chooses Copy, including when combined with another modifier; every other modifier combination chooses Move. Check `possibleActions()` before setting the Qt action; if the required action is unavailable, reject with a reason rather than allowing Qt's fallback action to disagree with the operation.
4. Separate **event admission** from **transfer eligibility**. The designated Folder Items and tab drop surfaces accept drag-enter and drag-move for delivery, even when the pure preview rejects the source or target, so Qt can send the release. Show no eligible outline for a refused preview and provide an ineligible visual cue without announcing a failure during hover; do not treat an admitted Qt event or its cursor as file-operation approval. On release, clear hover and call authoritative `AcceptDrop` exactly once for a decoded live token and observed typed target, regardless of the last preview count. Let it emit `DropChecking` or `DropRejected`. Decode, provenance, or target-identity failures take a separate typed rejection route, including external and malformed payloads; `dropEvent` then ignores the file transfer. No native MIME content constructs an `OperationIntent`. Test the actual platform cursor separately: if macOS shows an allowed badge during delivery-only admission, the ineligible cue and post-release reason must remain unambiguous, and the guided check records that limitation.
5. Extend the CXX-Qt bridge and session API so `drop_target` failure, a missing session, or failed token decoding cannot return a silent `false`. Use explicit reasons such as `ExternalSource`, `InvalidPayload`, and `StaleTarget` where appropriate, while keeping unknown or replayed tokens distinct. Validate that `QDropEvent::source()` is one of this workspace's registered live Folder Items Lists and matches the captured Browser; a mutable widget property alone is insufficient provenance. Route native rejections through a target-Browser output that the existing presenter can show and announce, with a safe fallback if the session is unavailable. Keep immediate and asynchronous `DropRejected` outcomes brief and specific in the target Browser Status Bar. Keep `Workspace` transfer safety, frozen roots, typed target, canonical preflight, `OperationIntent::transfer`, safety journal, and ordinary operation coordinator authoritative.
6. Extend `desktop_checks.cpp` and `scripts/check-file-drag-drop.sh` with events delivered to the actual widgets, covering press, threshold, release, modifier transitions, selected and unselected rows, eligible and ineligible list and tab targets, immediate and late rejection reasons, and one-use acceptance. Keep completed Copy/Move filesystem assertions and add any missing target-class and direction coverage. Run `scripts/check-folder-items-context-menu.sh` to protect exact Shift-secondary-click routing, and include primary-versus-secondary sequences in the native drag check. Use guided real-pointer macOS acceptance for physical Control-click, native threshold, cursor badge, and rejected release because synthetic events cannot establish those platform behaviors.

## Verification and sequencing

The owner-directed current-folder cue is a small child of each Folder Items viewport, revealed only for a live internal drag and removed when the native drag session ends. Its label stays visible over a full list. Its hover and release map to the existing `BrowserFolder` target (`kind = 0`, active tab ID, no row); native source provenance, drop-time action classification, stale-tab observation, typed rejection, and physical preflight match the list's Browser-folder path. It neither resolves a row beneath the cue nor changes selection, focus, or navigation. The desktop window shows and hides both cues around `QDrag::exec`; the disposable native check sends drag events directly to the cue and verifies Copy/Move preview, malformed refusal, and a completed Move.

Adjust the native helpers and gesture code, then run focused application and native checks while iterating. A test that invokes the bridge directly proves policy and filesystem effects; a widget-delivered offscreen event test proves Qt handler ordering; neither proves physical macOS pointer behavior. Complete guided pointer acceptance in a disposable profile, then run `make check` once as the milestone gate. P4-M7's pending real-pointer item should be reconciled with the M12 evidence before either milestone is marked Done.

The native check uses a source seam on the list and tab widgets only when both `DUAL_PANE_INTERNAL_FILE_DRAG_DROP_ROOT` and `DUAL_PANE_TEST_PROFILE` are set. It supplies a registered live Folder Items widget while sending synthetic Qt events to the target widgets, because Qt's offscreen drag loop does not supply `QDropEvent::source()` for those synthetic events. The normal path always uses Qt's event source and still requires the registered-widget and application-token checks. The seam proves handler ordering and Status Bar delivery in an isolated profile; the guided physical run remains the proof for platform pointer and cursor behavior.

The existing AppKit bridge in `keyboard_layout.mm` also reports whether the native event under Qt delivery is a physical primary or secondary mouse press, drag, or release. `FolderItemsList` uses that fact when Qt presents a physical Control-primary sequence as right-button mouse events, and suppresses the context-menu event for a physical primary press. A true secondary-button event keeps the Context Menu route. A disposable-profile-only native check seam simulates that remapping alongside the ordinary right-button sequence; the guided real-pointer run must still confirm what macOS and Qt actually deliver on this machine.
