# P3-M8 architecture

Status: Active

P3-M8 supplies the outer-ring half of the P3-M7 workflow: a native gateway behind the scan, execute, and cancel requests, plus the presentation of operation state. It also extends the P3-M7 contract where native work showed gaps: folder finalization, name problems, job dismissal, byte progress, and opening.

## Application contract extensions

Each extension stays Qt-free, is tested without a runtime, and leaves the P3-M7 tests passing.

- **Error kinds.** `OperationErrorKind` gains read-only, privacy-restricted, changed-since-scan, unsupported item, Trash unavailable, source-removal-failed, journal-unavailable, and folder-not-empty, all recoverable with Try Again/Skip/Cancel. There is no internal error kind. `scanned()` turns any non-executor failure into a Skip decision, and a `Failed` step cannot carry completed work, so a panic or lost worker reuses the `OperationExecutorUnavailable` terminal event. That event already ends as Failed or Partial, or as CleanupUncertain while cancelling.
- **Folder finalization.** The P3-M7 step contract cannot report a failure on a folder removed after its contents: errors must name `plan[at]`, `Finished` rejects new failures, and `Execute` carries only scan skips. Permanent deletion and moves therefore end their main pass without removing source directories. The application then builds a finalization list: the plan's directories, deepest first, minus every ancestor of a scan skip, decision skip, or failure. It issues `Finalize` steps over that list with their own index and progress. A step result advances, raises a recoverable error naming the current directory, or finishes, and the existing decision, token, and cancellation rules apply. A directory already absent counts as finalized, which covers subtrees moved by one atomic rename. A directory holding new content raises folder-not-empty. `unavailable()` handles the finalizing state like Running, so a lost worker cannot strand the job.
- **Name problems.** `StepResult::NameCollision` and `OperationStatus::NameCollision` keep their P3-M7 shape for a collision. Sibling `NameRejected` variants carry a typed `NameProblem` for a name that is too long or has characters the volume rejects; `NameRejected` with `NameProblem::Collision` is treated as `NameCollision`. `OperationJob::name_problem()` reports all three alike. The editor stays open, and it shows the existing pre-job rejections the same way: `InvalidName` and names `EntryName` cannot represent, such as a slash or NUL. Retrying through `Command::RetryName` cancels the rejected job, which closes without cleanup, and starts a new intent from the rejected job's frozen folder and target; an invalid retry keeps the rejected job. Committing an unchanged name is answered by the existing `UnchangedName` rejection, which presentation treats as closing the editor.
- **Availability.** `operation_availability` needs a name for Rename and New Folder, and a placeholder could produce false `UnchangedName` or `InvalidName` results. A name-less query per command serves menu enablement. A refused shortcut continues to produce `OperationRejected { reason }`, which presentation turns into the Status Bar message.
- **Refresh at terminal outcome.** Architecture 4.3 step 8 has the application request refreshes itself; `LocationInvalidated` remains the runtime's input for observed changes. After any terminal outcome with completed entries, the application rereads every open tab in either Browser whose location is the source or destination folder, or lies at or below a source or destination root. A tab whose folder is gone keeps its rows and shows the Missing Folder Overlay.
- **Post-edit selection.** One pending `(tab, folder, name)` record is applied when a matching listing arrives and then cleared. Navigation, a selection change, or a listing without the name also clears it.
- **Dismissal.** `OperationCoordinator` keeps every job today. A `DismissOperation` command removes a finished job when its panel hides or closes. A job that finished before its panel was revealed is dismissed once its Notice is recorded. Running and waiting jobs refuse it.
- **Byte progress.** `Event::OperationProgress { id, generation, bytes }` travels through the application like every other result. It is checked against the step generation, stored on the job for display, and never consulted for decisions. The runtime coalesces it per operation.
- **Packages.** The Context Menu and activation must know a package without a round trip, so the directory reader marks bundles on its worker. It calls the reentrant `QFileInfo::isBundle` through the C++ bridge for directory entries only, and `Entry` gains a package flag. Copy and Move still treat a package as a directory.
- **Opening.** Activation uses the entry's kind and package flag through `Entry::activation`; `can_enter` still drives folder-first sorting. Only a link needs an open-item request, including a link to a folder, which could point to a package: a worker resolves it to a regular file, a folder, a package, or something else. The application validates the result's token and emits an output asking presentation to open the target. The Qt call happens on the GUI thread because `QDesktopServices::openUrl` documents no thread guarantee. It reports only whether macOS accepted the request; a refusal returns as an event that adds an Open Failed Notice and opens Notices.
- **Notices.** New `NoticeKind` variants cover operation summaries, failures, partial results, journal unavailable, sweep reports, and open failures. The adapter owns wording. A summary is recorded for every terminal job that started work; a pending confirmation or a refused name closes without one. Failed, partial, and uncertain-cleanup summaries, journal unavailable, open failures, and sweeps with failures open Notices.
- **Actions.** Catalogue `CopyToOtherBrowser`, `MoveToOtherBrowser`, `RenameItem`, `MoveToTrash`, `DeletePermanently`, and `ShowPackageContents` with their decided defaults. `Key::Delete` already maps to the Mac Delete key (`Backspace`). Settings saved before these IDs existed load with defaults for them.
- **Quit.** `Command::Quit { confirmed: false }` with active jobs returns `QuitConfirmationRequired`; a pending confirmation or a refused name is not active. A confirmed quit, or one with no active jobs, cancels every unfinished job, returns `QuitAccepted`, and starts no new operation.
- **Journal status.** The runtime sends a journal-status event at launch and after each reopen attempt. Until the first event the journal counts as available; the executor still refuses to create a temporary without its journal record. While the journal is unavailable, Copy availability returns a new `OperationRejection` reason. The Journal Unavailable Notice offers Try Again, which asks the runtime to reopen it.

## Native gateway

The desktop crate gains an operation gateway on the file-operation lane described in [architecture 5.2](../architecture.md#52-planned-desktop-execution-model): two workers, bounded admission, runtime-owned write-scope leases, and one terminal claim per job. A worker owns copied request data only. Requests for one operation run in order: a cancel or cleanup runs only after that operation's in-flight step has stopped. A step yields with `Advanced` after a short time budget (about 200 ms) or at a decision. It publishes typed progress and releases its worker and leases before anyone is asked anything. Leases cover destinations, plus the source subtrees of move, Trash, and deletion.

- **Scan.** Walk each frozen root with no-follow metadata calls and emit the contiguous depth-first plan. Links are recorded as links. A failed directory read is a typed scan failure for the Try Again/Skip decision. The plan validator accepts a roots-only plan, so Trash scans only roots; Copy, Move, and deletion scan fully. Current-launch temporaries are never listed.
- **Revalidation.** Before each mutation, compare the item's identity (device, inode, kind, and size or mtime as appropriate) with the scan's record; a mismatch is changed-since-scan. Also walk the destination's device and inode ancestry: if it reaches a source root, the domain's path-component check missed a symlinked or case-variant path, and the item is rejected.
- **No-clobber.** An `lstat` of the destination is only a fast path that avoids copying data for an obvious conflict. The authority is the write primitive: `mkdir` for directories and `renamex_np` with `RENAME_EXCL` for files and links. `EEXIST` becomes the conflict result and the temporary is discarded. A Replace revalidates the destination's identity immediately before its `rename()`, which narrows but does not eliminate the race.
- **Temporary-then-move.** Files, links, and cross-volume targets are created as `.dual-pane-<launch>-<operation>-<n>.partial` in the destination folder, which keeps the final move on one volume and atomic. Directories are created directly; an empty directory the operation created remains as completed work after cancellation.
- **Copy.** `clonefile` on the same APFS volume, else `copyfile` with all metadata and `COPYFILE_NOFOLLOW`. Links are copied as links; special files raise unsupported item. The `copyfile` callback publishes byte progress and checks the cancel flag.
- **Move.** A same-volume file, or a directory whose destination is absent and whose subtree holds no scan-skip placeholder, moves with one `RENAME_EXCL`. The result is `Advanced` with the subtree counted as completed. Otherwise entries move one by one: same-volume replacement is a single `rename()`, cross-volume goes through a temporary, verify, then source removal. Source directories are left for finalization.
- **Rename.** Use `RENAME_EXCL`. On `EEXIST`, if the destination resolves to the source's device and inode, read the parent directory. If no separate entry has the exact destination bytes, the volume has matched the same entry under a case or normalization variant, so perform a plain `rename()`. Otherwise it is a hard link, which is a real collision. Identity decides this, never a name comparison, as [architecture 4.4](../architecture.md#44-data-safety-invariants) requires. `ENAMETOOLONG` and the volume's invalid-name errors become name rejections.
- **Trash.** `QFile::moveToTrash` from the C++ bridge, one root per call. Qt's docs state no thread guarantee, so a temp-directory test decides: worker thread if safe, otherwise a serialized GUI-thread queue, one root per turn, cancellable between roots. Qt reports only success or failure, so a failure maps to Trash unavailable, never to deletion. The runtime reports `LocationInvalidated` for the parent of the returned `pathInTrash`.
- **Permanent delete.** The main pass unlinks files and links with `unlinkat`, never following links. Finalization removes directories with `rmdir`, deepest first.
- **Cancellation.** Check a shared flag before each side effect, between units, and in the `copyfile` callback. Remove only this operation's temporaries. If cleanup cannot prove a safe result, report uncertain cleanup.
- **Errors.** Map `errno` to the application error kinds at the edge and keep raw errors in logs only. Each job runs behind a panic boundary and publishes the executor-unavailable terminal event without replaying the step. A fresh worker then removes that operation's temporaries using its journal records and the exact name pattern. Anything it cannot remove stays recorded for the next launch.

All `unsafe` stays in one small `libc` wrapper module with a `// SAFETY:` comment per block; the policy stays out of it.

## Safety journal

A separate SQLite file beside the settings database, written through `rusqlite` by one serialized runtime writer. It never shares a connection or transaction with settings, and the Reset Settings code, which moves the settings database and its sidecars aside, never names it.

At launch, the runtime reads 16 bytes from `getentropy` as the launch ID. Before an operation's first temporary in a destination directory, the gateway writes one durable record `(launch, operation, directory, device)` and waits for it. After cleanup confirms that no temporaries remain, at terminal outcome, the record is deleted. So there is one write per operation and directory, not per file.

At the next launch, the sweep processes each record from an earlier launch. It lists the directory and removes only regular files or links whose names match `.dual-pane-<launch>-<operation>-*.partial` exactly, never following links or touching directories, then deletes the record. A missing directory drops its record. An unreachable volume keeps the record silently for a later launch. Notices reports removals and failures, and failures open Notices.

If the journal cannot open, Copy is disabled through the journal-status event, and the Journal Unavailable Notice offers Try Again. A move learns whether it crosses volumes only during execution, so a cross-volume item raises journal-unavailable, and Try Again reopens the journal. Rename, same-volume move, Trash, deletion, and New Folder use no temporaries and continue. The journal uses WAL with default durability, which survives a process crash; a power loss can lose the newest record, and the leftover temporary then stays visible after relaunch.

## Presentation

Follow the existing MVVM path: application output, presenter, bridge model, widget.

- **Entry points.** The input controller maps menu items and shortcuts to the existing intents. Each catalogued action carries its shortcut scope (`ActionId::scope`), and the Qt binder installs shortcuts from it alone: file-command shortcuts act only while the Folder Items List has focus; New Folder is window-wide; only Quit works in every window and while an inline editor has focus. Disabled menu items stay disabled, and a refused shortcut shows its reason in the source Browser Status Bar for about three seconds.
- **Inline editors.** `InlineNameEditor` commits synchronously today. The file editors add a pending state between commit and the job's result. A name rejection reopens or keeps the editor with the typed name and the error, including after focus loss. Other failures close it, and the job's panel shows the card. The New Folder Name Editor is an empty temporary row pinned at the top of the listing.
- **Operation Panels.** One view model per job, driven by job output. The reveal timer (about 500 ms) belongs to the presenter; a decision, failure, or partial result reveals immediately. Cards are per job, concurrent, never take focus, and have no default button. For keyboard access, floating panels are regular windows that join macOS window cycling (``Command+` ``), and docked panels are in the main window's Tab order. Floating panels are their own windows with their own `Command+W`. A docked panel needs focus-aware routing, so `Command+W` reaches the panel instead of closing a tab. Panel position is session-only presentation state. Hiding or closing a finished panel sends `DismissOperation`, and so does recording the Notice for a job that finished before its panel was revealed.
- **Missing Folder Overlay.** The presenter shows centered “Command+R to Refresh” text over dimmed last-good rows for `ItemMissing` and `NotADirectory` and removes it after a successful listing. The narrow-Browser Expand overlay takes precedence.
- **Quit.** `QCoreApplication::quit` delivers a close event to each window, so the main window's close handler covers Command+Q, Dock Quit, and the close button. With running jobs it ignores the close and shows the confirmation. Confirming cancels every job, closes delivery, and exits the event loop; it never waits inside that loop. The composition root then joins the file-operation workers with a bound of about five seconds, and anything left over is swept at the next launch.

## Verification

1. **Native tests in temporary directories:** each operation kind; conflicts, merge, kind mismatch, links; same-volume and injected cross-volume moves; finalization with skipped content and removal errors; case-only rename and hard-link collision; destination within source through a symlink; revalidation mismatch; cancellation mid-copy; forced failure during Replace; panic containment; journal crash and sweep; Reset Settings leaves the journal alone; whether Trash is thread-safe.
2. **Application tests:** the contract extensions, with the P3-M7 suite unchanged.
3. **Runtime and bridge tests:** admission, lease serialization, per-operation ordering of cancel after a step, time-budget yields, coalesced progress, exactly-once terminal events, stale results, and decision round trips.
4. **Presenter and widget tests:** panel and card state, reveal timing with a fake clock, Status Bar expiry, shortcut focus scope, editor pending and reopen states, Notices entries, refresh targets, the overlay, and the quit prompt.
5. **Human check at the end** for drag-docking, real Trash, default-application and package opening, card focus and announcements, and visual behavior. Then run the repository gate.

## Risks

- `clonefile`, `copyfile`, and `renamex_np` behave differently across volumes and file systems; tests build what they can in temporary directories and inject the rest.
- Provider-backed files, such as dataless iCloud Drive items, may download while being copied; the `copyfile` callback keeps them cancellable, but progress can stall.
- A Move scans its whole tree before executing even when one rename would do; only Trash scans roots alone.
- Real Trash and default-application opening have no safe automated test; they rely on the human check.
- Floating-panel drag-and-dock and focus-aware `Command+W` are the largest widget tasks and have no precedent in the codebase; build them last.
